# pi-ui

A minimal, single-conversation web UI for the [pi](https://www.npmjs.com/package/@earendil-works/pi-coding-agent) coding agent, with one durable conversation and no session management. It installs as a PWA and accepts text, titles, and URLs from the native share sheet on platforms that support Web Share Target.

It ships as `ghcr.io/naqerl/pi-ui`. The container has no credentials baked in: your real pi agent directory is bind-mounted at runtime, so the UI uses your `auth.json` and the model catalog configured there. The conversation is stored in SQLite by `@earendil-works/pi-durable`; the workspace host directory holds pi's working tree together with that database and a small durable run marker, so a whole session survives container replacement and a process restart mid-run. Context compression runs in-process through `billion-context`; its fold state lives in a third host directory, `~/.local/share/billion-context`, which must also be writable and persistent. Those three host paths are the only mutable state; the image is otherwise stateless. A fourth, read-only mount of `${ZEROSHOT_CONFIG_DIR:-$HOME/.config/zeroshot}` supplies the hub token that the MCP `Authorization` header reads.

## Quick start (local)

```sh
npm install && npm run build && npm start
```

Open the URL printed by the server (by default <http://localhost:8787>). The server and the Vite client share the same origin in production; `npm run dev` runs the API on port 8787 and Vite on <http://localhost:5173>.

The browser suite is offline by default: `npm run e2e` starts the built server against a temporary `DATA_DIR` and a local fake OpenAI-compatible endpoint. Set `PI_E2E_LIVE=1` to run the opt-in live-model spec instead (it is skipped otherwise).

## Run the container

```sh
docker pull ghcr.io/naqerl/pi-ui:v1.4.1

docker run -d --name pi-ui --restart unless-stopped \
  --network host \
  -v "${PI_WORK_DIR:-$HOME/pi-work}:/workspace" \
  -v "${PI_AGENT_DIR:-$HOME/.pi/agent}:/home/pi/.pi/agent" \
  -v "${BILI_DATA_DIR:-$HOME/.local/share/billion-context}:/home/pi/.local/share/billion-context" \
  -v "${ZEROSHOT_CONFIG_DIR:-$HOME/.config/zeroshot}:/home/user/.config/zeroshot:ro" \
  ghcr.io/naqerl/pi-ui:v1.4.1
```

Open <http://localhost:8787>. The host working directory defaults to `~/pi-work`; create it first if `$HOME/pi-work` does not exist. The agent directory defaults to `~/.pi/agent`, which is the directory pi already uses on the host. Create the compression-state directory before the first run too: `mkdir -p ~/.local/share/billion-context`. Host networking and the read-only config mount are required for the hub MCP server; see [Why host networking](#why-host-networking).

The compose file is the same setup with the paths and comments in one place. It uses `network_mode: host` and has no `ports:` mapping:

```sh
docker compose up -d
# or build the image locally instead of pulling it
docker compose up -d --build
```

The host paths can be overridden with environment variables:

```sh
PI_WORK_DIR=$HOME/pi-session PI_AGENT_DIR=$HOME/.pi/agent PORT=9000 docker compose up -d
```

### What comes from the mounts

| Host mount                                             | Container path                          | What lives there                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------ | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `${PI_WORK_DIR:-./work}`                               | `/workspace`                            | pi's working tree, everything a session creates, and the durable conversation in `data/` (`pi.sqlite3` plus `current.json`). This is the single directory that backs a whole session.                                                                                                                                                                                 |
| `${PI_AGENT_DIR:-$HOME/.pi/agent}`                     | `/home/pi/.pi/agent`                    | Your real pi state (`PI_CODING_AGENT_DIR`): `auth.json`, `web-search.json`, `models-store.json`, `settings.json`, optional `mcp.json`, model overrides, installed pi packages, and pi's own history/state. Mounted read-write because pi writes here. This mount supplies the provider credentials for both pi and billion-context, and is trusted MCP configuration. |
| `${BILI_DATA_DIR:-$HOME/.local/share/billion-context}` | `/home/pi/.local/share/billion-context` | billion-context's in-process fold state: session files, `index.db`, and logs. Must be writable by uid 1000 and persistent.                                                                                                                                                                                                                                            |
| `${ZEROSHOT_CONFIG_DIR:-$HOME/.config/zeroshot}`       | `/home/user/.config/zeroshot`           | Read-only zeroshot configuration. The hub token at `hub/api-token` is read by the `!`-prefixed `Authorization` command in `mcp.json`; without this mount the header cannot be produced and the hub server disappears.                                                                                                                                                 |

`data/` is not a separate mount: it lives inside the workspace mount, so replacing the container keeps both the files pi worked on and the conversation that produced them. The compose file sets `DATA_DIR=/workspace/data` explicitly for the same reason.

These three are the only mutable paths, and the image is otherwise stateless. The zeroshot config mount is read-only. The image contains no `auth.json`, no `web-search.json`, no `models-store.json`, and no API keys; that state reaches the process only through the agent-directory mount. The workspace and billion-context mounts hold session data, not credentials.

### Why host networking

The hub MCP server listens on the host's loopback interface only, and `mcp.json` addresses it as `http://127.0.0.1:7383/mcp`. Under Docker's default bridge network, `127.0.0.1` inside the container is the container itself, so the hub is unreachable even when it is healthy on the host. The same `mcp.json` produces its bearer header with an `!`-prefixed command, `!echo Bearer $(cat /home/user/.config/zeroshot/hub/api-token)`; that command runs inside the container at boot, so `${ZEROSHOT_CONFIG_DIR:-$HOME/.config/zeroshot}` must be mounted at the same absolute path.

Neither failure is fatal, which is why it degrades silently. The tell is two boot lines: per-server unavailability, then a smaller tool count.

```
mcp: server zeroshot is unavailable
tools: read + bash + edit + write + 22 MCP tools (tracer, zeroshot, web) + 6 billion-context tools
```

With host networking and the config mount the second line reports 46 MCP tools instead. The app also surfaces the same state: `/api/state` lists each configured server under `mcp.servers` with `available`, and the MCP widget on the stats page marks `zeroshot` as `unavailable` when it failed. When every server starts, each row reads `connected` with its tool count.

### Context compression state

Billion-context is installed in inline mode. Its engine runs inside the server process and listens on the virtual origin `http://billion-context.inline`; an outermost fetch wrapper stamps each model request with the current durable conversation ID. The engine keeps its own session files and SQLite index under `~/.local/share/billion-context` (honoring `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, and `XDG_STATE_HOME` when set). That directory must be writable by the process and mounted persistently, or compression history is recreated after every container replacement. It does not contain credentials; provider credentials still come from `PI_CODING_AGENT_DIR` (`auth.json`) and the environment. Losing this directory costs compression continuity, not the durable chat transcript, which remains in `<DATA_DIR>/pi.sqlite3`.

### Updating the bridges

`@earendil-works/pi-durable`, `@earendil-works/pi-ai`, `@realmikekelly/pi-mcp-adapter`, `@realmikekelly/pi-mcp-events`, `billion-context`, `pi-web-access`, and `typebox` are pinned to exact versions: `package.json` has no `^` or `~`, and the committed `package-lock.json` is the resolved tree. Bump one package at a time, then rebuild the lockfile and run the same check the release reviewer runs:

```sh
npm install --save-exact <package>@<version>
npm install --package-lock-only
DATA_DIR=$(mktemp -d) node scripts/bridge-check.mjs --all
```

`node scripts/bridge-check.mjs --all` is the default. `--bili` checks only the durable conversation, model catalog, and billion-context wire bridge; `--web` checks only the built-in `pi-web-access` server. The report is four lines:

```
durable   conversation=<id> entries=<n> resumed=<bool>
models    provider=<p> model=<m> credentials=<found|missing>
bili      origin=<origin> header=<header>=<id> rewritten=<n> status=<ok|unavailable>
web       tools=<n> [web_search fetch_content get_search_content source_check] child=<alive|missing>
```

A changed line is the review surface. A different `header=` means the billion-context conversation identity header was renamed. A changed `rewritten=` or `status=unavailable` means model requests no longer reach the inline engine. A different `tools=` or tool list means the MCP server's schemas changed.

Exit codes are `0` when every selected part is green, `1` when a required part is missing, and `2` when the only problem is missing provider credentials. The check always uses the throwaway `DATA_DIR` you pass, so it never opens the real conversation database, and it closes the MCP runtime before exiting.

Two bumps break silently because neither the UI nor a normal model turn fails outright:

- **A new header name.** The identity header is `x-bili-plugin-conversation`; its constant, the wrapper, and this report live in `src/server/billion-context.ts` and `scripts/bridge-check.mjs`. If a bump renames it, look for the new name in the installed `billion-context` entry (`node_modules/billion-context/dist/agent/pi-native.js`) and update the wrapper and check together.
- **A new `plan.mode`.** Billion-context's mode planner lives in `node_modules/billion-context/dist/agent/pi-native.js`; search that file for `plan.mode` after a bump. A new mode can change how a request is planned without failing the request, so `rewritten=` and `status=ok` are the only signals in the report.

For a `pi-web-access` bump, compare the MCP tool schemas in the installed package's `dist/mcp-tool-definitions.js` (bundled into `dist/mcp-cli.js` in 0.44.0) with the names listed by `web ... child=alive`. A renamed tool is a breaking bridge change even when the server still starts. For an adapter or events bump, run the MCP e2e specs; they exercise tool listing, a round trip, a broken server, and the event subscription.

## Configuration

| Variable              | Meaning                                                                                                                                                                              | Default                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| `PORT`                | HTTP port for the server.                                                                                                                                                            | `8787`                       |
| `PI_CWD`              | Working directory pi operates in. Must exist or the server refuses to start.                                                                                                         | `process.cwd()`              |
| `DATA_DIR`            | Directory for `pi.sqlite3`, `current.json`, `tasks.json`, `dashboard.json`, attached images in `media/`, and the durable `run.json` marker. Relative paths resolve against `PI_CWD`. | `<PI_CWD>/data`              |
| `PI_MODEL`            | Initial model, as `provider/model-id` or a model id. A choice in the pi menu is stored on the conversation and kept across restarts while that model remains in the catalog.         | pi's configured default      |
| `PI_CODING_AGENT_DIR` | pi configuration/auth directory. In the image this is `/home/pi/.pi/agent`, bind-mounted from the host.                                                                              | pi's `getAgentDir()` default |

The durable conversation is stored at `<DATA_DIR>/pi.sqlite3` (by default `<PI_CWD>/data/pi.sqlite3`). `<DATA_DIR>/current.json` records the single current conversation ID. `<DATA_DIR>/tasks.json` is the todo ledger. `<DATA_DIR>/run.json` is the run marker: it is written with a temporary file plus rename before a run is admitted and records the user message, start time, queue/steer mode, queued messages, whether a stop was requested, and whether an automatic continuation already happened. On boot the server resumes that conversation when the database still has it; otherwise it creates a new one and rewrites the file. The directory is created on first boot and is intentionally git-ignored.

If the process is killed during a turn, the next boot keeps the committed transcript, marks the last assistant text `partial`, appends a system note, and reports `interrupted` in `/api/state` and the chat banner. Unless a stop was requested, it then submits exactly one continuation as a steered turn, guarded by a durable request id and the marker's `autoContinued` flag. Queued messages from the marker are restored as queued follow-ups. An explicit `SIGTERM`/`SIGINT` leaves the marker in place; a normal completion, a stop, or a drained queue clears it.

On boot the server logs the working directory, database path, conversation ID, whether it was resumed, and whether the previous run was interrupted. It also logs the selected model, or a clear warning when no credentials are available. The registry contains the coding tools (`read`, `bash`, `edit`, `write`) and the task tools (`task_list`, `task_done`, `task_block`), plus tools from the configured MCP servers and the built-in `web` server (`web__web_search`, `web__fetch_content`, `web__get_search_content`, `web__source_check`, from `pi-web-access`). `tool_search` is installed whenever MCP tools exist so they do not inflate the system prompt. When the inline engine answers `GET /__bili/plugin/manifest`, the registry also exposes its compression tools (`compress`, `decompress`, `search_context`, `acp_status`, `acp_cache`, `acp_read_original_image`); if the manifest is unreachable those tools are absent and the rest of the server still boots. Coding-agent extensions and codemode are not loaded; MCP goes through the dedicated adapter described below.

## MCP

`src/server/durable-extensions.ts` is a deliberately small `ExtensionAPI` shim: it exposes `registerTool`, one shared `events` emitter, `on`, and `sendMessage`, backed by the durable conversation. There is no general extension loader. `src/server/mcp-runtime.ts` uses `createHostManagedMcpAdapter` from `@realmikekelly/pi-mcp-adapter` to connect MCP servers and the `mcp_events` tool from `@realmikekelly/pi-mcp-events` to relay server events.

**Configuration.** Servers come from `${PI_CODING_AGENT_DIR:-~/.pi/agent}/mcp.json`, under `mcpServers` (or `servers`). Both streamable-HTTP entries (`url`, optional `headers`/bearer token) and stdio entries (`command`, `args`, `env`, optional `cwd`) are supported. Each entry may set `requestTimeoutMs` in milliseconds (default `30000`). Header values beginning with `!` are resolved once at boot by running the rest of the value as a command; `!!` escapes a literal `!`, and `${VAR}`/`$env:VAR`/`{env:VAR}` references are expanded from the environment. Resolved header values and tokens are never logged, returned in a tool result, included in an error, or exposed through `/api/state`; tools may name a server, but never echo its configuration. If `mcp.json` has no `web` entry, the bundled `pi-web-access` server is added as a stdio server (`node <pi-web-access>/dist/mcp-cli.js`). A missing or unreadable `mcp.json` simply means no user MCP servers.

**Tool names.** A server tool is exposed as `<server>__<tool>`, for example `github__search_issues`; characters outside `[A-Za-z0-9_-]` in the server name are hex-escaped. Names are registered as deferred tools, so the model discovers them with `tool_search` before calling them. A tool call is dispatched at most once. Failures report their delivery class: `not_sent` when the request never left the host, `may_have_run` when it may have reached the server but its outcome is unknown, `server_error` for a reported server-side failure, and `invalid_result` when the response could not be interpreted. Each server uses its configured `requestTimeoutMs`, or 30 seconds when unset. A `401` or `403` from an HTTP server produces only `server <name> rejected the configured credentials`, with no header or token content.

**Events.** The runtime registers the `pi-mcp-adapter:protocol:v1` bridge that `pi-mcp-events` requires, emits `session_start` at boot and `session_shutdown` on close, and installs `mcp_events` with operations to list event catalogs and open or cancel a subscription. Received event notifications are batched and injected into the durable conversation as follow-up messages. Closing the server cancels subscriptions; a reopened process starts a fresh session. A live subscription whose server answers the open stream with JSON-RPC Invalid Request (`-32600`) is closed and opened again on a new connection. Method-not-found and rejected credentials still end that subscription.

**Partial failure and trust.** Each server connects independently. A server that fails to start is reported by name and skipped; it contributes no tools, and the remaining servers and the rest of the UI still boot. The same availability is exposed by `/api/state` under `mcp.servers` (with each server's registered `tools`) and `mcp.unavailable`, and the default MCP widget on the stats page lists every configured server, so a configured-but-unreachable server shows there as `unavailable` and is never invisible. The model's `bash` tool runs with the server process's access, so it can read the mounted agent directory and any secrets stored there, including `mcp.json`, header values, credential files, and `web-search.json`. Treat the mounted agent directory as trusted only for that model: anything readable under it is reachable by `bash`, not merely by the server. `mcp.json` can also point at arbitrary local commands, just like pi's own config, so keep it trusted and avoid storing secrets in world-readable files.

## Background jobs

The agent can run long shell commands without blocking a turn. `job_start` launches a command with `bash -lc` in the agent's working directory as its own process group and returns at once with an id (`j1`, `j2`, …). `job_list` shows running and recent jobs, `job_output` reads a job's combined stdout and stderr by offset or as a tail (at most 20,000 characters per call), and `job_cancel` stops a job (SIGTERM to the group, then SIGKILL after 5 seconds). When a job ends on its own, pi queues a message for the agent with its exit code, duration and last 20 output lines. If the agent is idle, this starts a new turn; otherwise the message waits for the current run to finish. Cancelled jobs and jobs started with `notify: false` send the agent nothing. Job results never appear as user messages in the chat; the activity page has a row at the point each job ended, such as `job build finished ✓ 12s`, and opening it shows the command, status, exit code, duration and last output. Results for cancelled and `notify: false` jobs are stored as activity entries the agent never reads. At most 8 jobs run at once. The 50 most recent finished jobs and all logs are kept under `DATA_DIR/jobs`. If the server restarts while a job is still running, it keeps watching the job's pid. A job whose process is gone is marked `lost`, because its exit code can no longer be read. A container restart ends every running job.

## Dashboard

The page left of the chat is a dashboard of widgets the agent builds with `dashboard_get`, `dashboard_upsert`, `dashboard_remove`, `dashboard_push` and `dashboard_layout`. A widget is a stat, list, table, sparkline, markdown block or status list. Its data comes from pi-ui itself (context, tokens, cache, MCP servers, MCP events, jobs, session), from a JavaScript poll script, or from data the agent pushes. Poll scripts run in an isolated worker with `fetch` and the server's `env`, at most every 30 seconds and only while someone has the page open. A failing poll keeps its last value with a `stale` badge, and after 5 failures in a row it backs off and tells the agent once. The page shows data only: no HTML, scripts or buttons from widgets. A long press, a right click or the `⋯` button on a card removes it. Widgets and layout live in `DATA_DIR/dashboard.json`; tokens stay in the environment and token-looking text is masked. [docs/dashboard.md](docs/dashboard.md) has the tool schemas, mapping paths, limits, and a live Hetzner servers example.

## Install and share

- **iOS / iPadOS:** open the site in Safari, choose Share, then **Add to Home Screen**.
- **Android:** open the site in Chrome and choose **Install app** (or Add to Home screen).
- **Desktop:** use the install control in Chrome or Edge's address bar.

Browsers require HTTPS (or localhost) for service workers and installation. After installation, platforms with Web Share Target support list **pi** in the system share sheet. A shared title, text, and URL are posted to `/share` as `application/x-www-form-urlencoded` fields; the server appends a user message containing the shared text and URL, starts one pi run, and redirects to `/`. The same intake is available as `/share?title=...&text=...&url=...` and is useful on platforms without a native share target.

## Interaction design

Consecutive tool calls and thinking blocks between two messages collapse into one muted, monospaced run-info line in the transcript, for example `▸ 2 tool calls · 1.2k in · 340 out · 12.4s`. The line sits on its own small surface-colored card with a border, so it stays readable over the moving dither. It shows the tool-call count, the input and output tokens spent on that work, and the total time; thinking blocks are not named there, and `/activity` still lists them. On a narrow screen the line wraps between those pieces instead of cutting them off, and the card is at least 36 px tall so it is easy to tap. A zero count is left out. Tokens appear when a model call recorded them, as input and output only. The time is the span of the group, and it keeps moving while that group is still live. Selecting that line opens `/activity?run=<group>` for that run only. The transcript never renders tool arguments, tool output, or thinking text. `/activity` with no query lists every tool call and thinking block in the conversation, each with an expandable disclosure for its arguments, result or error, and duration. That page is one opaque card inset by the same 0.75rem edge gap as the chat column, filling the rest of the screen. The heading and subtitle stay put while the rows scroll. A back link returns to the chat.

While a run is active, the composer shows a line above the field with the word `working` and a braille spinner. The line slides up when the run starts and down when it ends. The spinner advances every 80 ms on a fixed interval, and it becomes a static `⠿` under `prefers-reduced-motion: reduce`. The same preference drops the slide. The header does not grow a status row.

The page background is a warp dither of the active theme's background and a dimmed mix of its foreground. Those colors are passed as comma-separated rgb, including when the computed page color is oklch. It drifts on its own, holds still under `prefers-reduced-motion: reduce`, and does not follow the pointer. Phones drop the WebGL context of an installed app that sits in the background, and the shader library never rebuilds after that, which used to leave a blank white page until a restart. The background now remounts the dither with a fresh canvas when its context is lost or found lost on return (`visibilitychange`, `pageshow` from the back-forward cache, or focus), and the dither's container is painted with the theme background so a recovering canvas never shows white. The header and the composer dock sit on the top and bottom edges. On a wide screen each bar is `72ch + 2rem`, slightly wider than the transcript column; on a narrow screen that cap is the full width. The dither shows through the header. A foreground edge separates the header from the transcript and the composer from the transcript, including the left and right sides of both bars. The header labels line up with the message text, and the composer's vertical padding matches the header. The first message stays 16px below the header, and the last message stays 16px above the composer, on a wide screen and on a phone. While the message field is focused, the composer drops its home-indicator padding and the page follows the visual viewport, so the bar sits on the keyboard. The `↓ latest` control uses the foreground fill so it does not match a message bubble. The composer stays partly transparent and blurred until the message field is focused, then eases to a solid fill. The composer follows the visible viewport, so it stays above the mobile keyboard and does not jump while the URL bar collapses. On the chat page the placeholder is `Message pi`. Enter sends when the agent is idle and steers while a run is active; Shift+Enter inserts a newline. The textarea grows to about eight rows, and every send resets it to exactly one line. The action control is one icon button with no fill. Send and Steer use the same send mark, and both marks are the same size. Stop is a circle in the theme's destructive color with a white square, not one fixed red. Tapping Steer does the same thing as Enter during a run. The composer has no queue control. The `pi` wordmark opens a menu. Theme applies an Omarchy theme to the whole page, including the header, footer, and latest control. That choice is saved in `DATA_DIR/theme.json` and written onto the `<html>` element of the first response, so a load paints the saved theme instead of the default colors. With nothing saved, the response uses the current Omarchy theme. The image ships those theme colors and corner radii at `/usr/share/omarchy/themes` (no wallpapers), and uses Vantablack when the container has no current theme name. `POST /api/theme` with `{"slug":"<slug>"}` saves the same choice. In an installed app the system bars follow the theme too: the page keeps one `theme-color` meta set to the theme background and updates it on every theme change, and `/manifest.webmanifest` is served with `theme_color` and `background_color` set to the saved theme's background (hex or comma rgb only; anything else keeps the stock values), so the splash screen and Android's status and navigation bars match from launch. Android re-reads an installed app's manifest only on its periodic update check, about once a day, so the launch colors can lag one theme change behind until then. Model shows the current model id and lists every catalog model that has credentials, grouped by provider. Choosing one stores it on the conversation; the next turn uses it, and a restart keeps it while that model is still in the catalog. `GET /api/models` returns `{current, models}`. `POST /api/model` with `{"provider":"<provider>","id":"<id>"}` switches to one of those models. User and assistant messages sit on the surface color over that dither. Each user and assistant bubble ends with its local send time as `hh:mm` in the bottom-right corner; hovering it shows the full date. The header, footer, menu, and those bubbles use a different theme step, `lighter_background` when it is not the page color and `dark_background` otherwise, so those surfaces are not separated only by a border. Corner radius follows the theme's Hyprland `rounding`: Vantablack leaves it unset, so corners stay square, and Solitude sets `rounding = 6`, so buttons, the composer, bubbles, and code blocks round. There is no markdown editor or working-directory picker.

Assistant messages render a deliberately small Markdown subset from `marked` tokens: headings, paragraphs, emphasis, strong text, strikethrough, inline code, fenced code blocks, links, lists, blockquotes, tables, and horizontal rules. Links open in a new tab with `rel="noreferrer noopener"`. The renderer builds React nodes directly and never uses `dangerouslySetInnerHTML`; raw HTML is shown literally. Unclosed fences and half-typed links are tolerated while text streams, and the transcript is not remounted for each delta. Code blocks are monospace and horizontally scrollable, with no highlighting. Each has a `copy` button in its top-right corner that copies the block's text and reads `copied` for a moment; on a plain-http host without the clipboard API it falls back to a selection copy. Their corners use the same theme radius as the rest of the page. User messages are always rendered literally so code and Markdown they paste stay exactly as typed; `/activity` remains plain text. Long hashes, URLs and inline code break anywhere inside a bubble instead of pushing past its edge, while code blocks and tables keep their lines and scroll sideways inside the bubble.

Images can go with a message or a new task. The `+` button on the left of the composer opens the file picker, and pasting an image into the field works too. Each image is uploaded as soon as it is picked and shows as a thumbnail above the field, with a remove button, a pulse while it uploads, and its reason if the upload fails. Send waits until every image is up. A chat message can be images alone; a task still needs a title. Before upload, the browser redraws an image as a JPEG when it is not PNG, JPEG, GIF or WebP, is over about 3.5 MB, or is longer than 2048 px on a side, so it stays inside provider limits. `POST /api/media` takes the raw bytes with an image `Content-Type` (at most 10 MB, magic bytes checked) and returns `{id, mimeType}`; the file is stored content-addressed in `DATA_DIR/media` and served by `GET /api/media/:id`. `POST /api/message` and `POST /api/tasks` accept `attachments: [id]` (up to 8). Message images go to the model as image blocks after the text and come back from `/api/state` as `attachments`. When the selected model does not accept images, the message is refused with that reason instead of having pi-ai replace the images with an "image omitted" note. Task images show as thumbnails on the card; `task_list` reports `images=N`, and the `task_view` tool returns a task with its images, so the agent sees them when it opens the task.

While a run is active, Enter and the Steer button inject the draft into the running turn. Steers enter the run together at its next turn boundary, in the order sent: right after the current tool round, or after the answer being written when there is no tool call (durable `steeringMode: "all"`). Until then a steer shows at the bottom of the chat as `steer · pending`; `/api/state` lists these as `steers`. ArrowUp in an empty composer takes back the newest pending steer and puts its text and images back in the composer, and pressing it again takes back the one before; with text in the composer ArrowUp moves the caret as usual. `POST /api/steer/:id` with `{"action":"unsend"}` withdraws one and answers 409 once it has entered the run. A steered message appears in the transcript where it entered the run, with a small `steer` label. The composer does not queue follow-ups. Programmatic clients can still post `mode: "queue"` to `POST /api/message`; MCP event messages use that path so a subscription can wake the model. In the chat, MCP event and subscription status messages show as a one-line notice, such as `MCP github: push event`, and tapping one opens each event's server, name, id, time and pretty-printed payload. The agent still receives the full message. Those follow-ups use pi-durable and are mirrored in `run.json`, so a restart restores them. `POST /api/queue/:id` accepts `{"action":"cancel"}` or `{"action":"steer"}`, and `POST /api/stop` clears that programmatic queue immediately, without asking for confirmation, then stops the run.

Stats, the chat, and the task list are three pages of the same view, in that order from left to right; the app opens on the chat. The address bar stores the open page as `?page=stats`, `?page=chat` or `?page=tasks`, and a refresh returns to it. Dots in the center of the header show the current page, and selecting a dot moves there. A horizontal swipe does the same on a touch screen. A sideways trackpad scroll switches pages, and Alt plus a horizontal arrow does too. The stats page is a dashboard the agent can edit (see [Dashboard](#dashboard)). By default it shows the context size against the model's window, input and output tokens, cache reads and writes, the cache hit rate (cache read over input plus cache read plus cache write, since input excludes cached tokens), the conversation cost, each MCP server with its tool count and live event subscriptions, or whether it is unavailable or its auth was rejected, and the latest 20 MCP events, newest first. A value the server cannot report says `unavailable` with the reason, such as no model call yet, an unknown model window, or a provider that reports no price. On the tasks page the composer creates a task instead of messaging pi: the placeholder is `New task`, and Enter adds it. An empty list shows `No tasks yet.` as a small inverted label, in the same style as the `↓ latest` button in the chat. A title can be as long as the draft. Titles render inline Markdown: bold, italics, strikethrough, inline code and links, with line breaks kept. Block syntax such as lists or headings stays literal, and a link is shown underlined but is not clickable, because the whole card is the done button. When that add fails, the reason is shown above the composer and the draft stays. A failed card or menu action shows its reason on that card, or at the top of the menu while the menu is open. A tap on a card marks that task done, and a second tap reopens it. A long press opens the card actions on a touch screen, and a right click opens them on a desktop: subtask, blocker, and remove. Choosing `subtask` aims the next submission at that task, and `top level` aims it back at the list. The end of the header shows how many subtasks are done, as `x/y`. An open blocker shows `blocked by`, and a task with an open subtask cannot be marked done until those subtasks are done. The ledger is one list in `DATA_DIR/tasks.json`, shared by every browser on this server. It is a todo list with subtasks and blockers. The agent can list that ledger, mark a task done, and create a blocker for a task. An open page updates when it does. It cannot add a task that blocks nothing, reopen a task, or delete one, and it does not claim work, assign agents, or record evidence.

The header carries no MCP status. Live MCP subscriptions show on their server's row in the MCP widget on the stats page, and the `MCP events` widget lists the latest 20 events, newest first. `/events` still lists every subscription and the full event log on every connected client. Draft text is broadcast as a full snapshot with a revision, so a client that connects mid-run shows the same text as the others.

The transcript follows new output only while the reader is at the bottom (within about 48 px). Scrolling up detaches it; new tool calls and streamed text then leave the viewport alone and a `↓ latest` button appears, filled with the foreground color so it reads apart from the messages. Sending a message or selecting that button re-attaches to the end. Height changes above the viewport keep the top visible element anchored instead of jumping to the bottom. When a run finishes while the reader is still at the bottom, the transcript scrolls back so the final reply starts 16px below the header, with its run info row on top, and `↓ latest` stays available for the end. A reader who scrolled away during the run keeps their position.

Long sessions open fast: `/api/state` returns only the latest 30 messages (stretched back to the user message that starts that run), and `GET /api/history?before=<order>&limit=<n>` serves older pages. Scrolling near the top of the chat loads the next page above without moving what is on screen. The activity and events pages still load the whole history. Markdown in replies renders once a bubble comes within 800px of the viewport and shows as plain text until then; long tool output on the activity page is collapsed past 40 lines or 4000 characters; and the stats, tasks, activity and events views, the Markdown renderer and the background shader load as separate chunks. On a 548 message session this cut time to first render from about 2.0 s to 0.4 s on a throttled phone-sized viewport, and from 1.0 s to 0.1 s on desktop.

## Releases

`CHANGELOG.md` lists each release under a `## <version>` heading; add the next section with every change and bump `version` in `package.json` before tagging. The image ships the changelog. On start the server compares its version with `DATA_DIR/version.json`: after an update it appends the unseen changelog sections to the conversation as a context message for the agent, shows a one-line `Updated pi-ui from A to B` note in the chat, and records the new version. A fresh install only records the version; an existing conversation from before this check gets the current version's section. `GET /api/health` reports the running version.

Pushing a `v*` tag runs `.github/workflows/release.yml`, which builds and pushes `ghcr.io/naqerl/pi-ui` to GitHub Container Registry with semver tags, `latest`, provenance, and GitHub Actions layer cache. Tag `v1.4.1` publishes `:v1.4.1` (the tag the commands above use), `:1.4.1`, `:1.4`, and `:latest`; the `v`-prefixed tag is emitted explicitly with `type=semver,pattern=v{{version}}` because the plain `{{version}}` pattern strips the leading `v`. The workflow can also be started manually with `workflow_dispatch` to rebuild an existing ref. There is intentionally no build on every push to a branch.

The image is built for `linux/amd64` only. The release job does not run an emulated `linux/arm64` build, because the QEMU build does not fit the job budget; add it to `platforms` only after confirming it builds reliably in CI.

GHCR creates a new package as private on first push. Set the `pi-ui` package's visibility to public once in the package settings on GitHub; after that, `docker pull ghcr.io/naqerl/pi-ui:v1.4.1` works without authentication. The publish job prints the resulting tags and digest in the workflow run summary.

## What this deliberately does not do

- No chat list, conversation titles, create/delete/switch, or multiple sessions.
- No agent task claims, assignments, comments, or sync with an external tracker. The tasks page is one todo ledger.
- No accounts, authentication, telemetry, or analytics.
- No working-directory picker, settings page, or configuration UI beyond the pi menu's theme and model choices.
- No attachments, file browser, markdown editor, message editing, or retry controls.
- No codemode or general coding-agent extensions. MCP servers are limited to those in `mcp.json` plus the bundled `pi-web-access` web server; `tool_search` exposes their deferred tools on demand. Billion-context is not spawned as a proxy or extension: it runs in-process in inline mode and only adds its own compression tools when its manifest is reachable.
- No unit tests or component test framework. The browser suite under `e2e/` is the end-to-end gate.
- No syntax highlighting, syntax-aware code blocks, raw-HTML Markdown, or rich tool output in the transcript.

## SDK notes

The session layer is `@earendil-works/pi-durable` over `openNodeSqliteStorage()` at `<DATA_DIR>/pi.sqlite3`. User input goes through `Conversation.submit()`; queue mode uses its `whenBusy: "followUp"` support and steer mode uses `whenBusy: "steer"`, with steered input placed as the application entry kind `ui.steer`. Streaming comes from `watchEvents()` and is adapted to the same SSE event names in `src/server/chat-service.ts`; queue and run-start fields are additive on those frames. The coding tools come from `createCodingTools()` and are installed with `createRegistry()` and `defineExtension()`. The model catalog is built with the installed coding agent's `ModelRuntime.create()`, following `dist/core/model-runtime.js`: it reads `auth.json`, optional `models-store.json` overrides, and the built-in pi-ai provider catalog from `PI_CODING_AGENT_DIR`. The system prompt is still built by the coding agent's `createAgentSession()`/`DefaultResourceLoader` path from `src/server/pi.ts`, then stored as the durable conversation's `instructions`. `/api/state` reports usage (`input`, `output`, `cacheRead`, `cacheWrite`, `cost`) and context usage from durable usage documents. `PI_MODEL` selection is best-effort: if the requested model cannot be selected, the server warns and keeps the configured default instead of failing to boot. A model chosen in the menu is written with `conversation.configure()` and is kept on the next boot when it is still in the catalog; `PI_MODEL` fills in only when the conversation has no stored model or that model is gone. `GET /api/models` lists credentialed models, and `POST /api/model` switches the stored one and updates the billion-context model headers for the next request.

The run marker is implemented in `src/server/run-marker.ts` and recovered in `src/server/session.ts`; the server attaches it to `ChatService`, which owns the auto-continuation and queue restoration. `SIGTERM`/`SIGINT` call `ChatService.beginShutdown()` before closing the harness, so a run that ends during shutdown does not clear the marker. At bootstrap, before the durable harness exists, `src/server/billion-context.ts` imports `billion-context`'s pi-native entry, keeps its in-process fetch transport, and installs the pi-ui identity wrapper outermost. Every model request is rewritten to `http://billion-context.inline/bili/<provider URL>` and stamped with `x-bili-plugin-conversation` (read from `<DATA_DIR>/current.json`), `x-bili-plugin-agent: pi`, and — once the model catalog is available — the selected model's `x-bili-plugin-model`, `x-bili-plugin-context-window`, and `x-bili-plugin-max-output` limits. The wrapper passes the original method, headers, body stream, and response stream through untouched; it never buffers or re-serialises an SSE response. The one conversation is registered with `POST /__bili/plugin/register` after boot without blocking it. Because the wrapper resolves a single global `current.json`, this design assumes the UI's one-conversation model; a future multi-conversation feature must stamp from the request's durable conversation instead. Automatic pi-durable compaction is disabled so billion-context owns compression; manual compaction still works. `node scripts/bridge-check.mjs --all` prints the durable conversation, model credentials, billion-context origin/header/rewrite/status, and the web MCP tools/status in one report; `--bili` and `--web` select one side. The check uses a throwaway `DATA_DIR` and closes the MCP runtime before exiting.
